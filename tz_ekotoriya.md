# Техническое задание
## Проект «Экотория» — интернет-магазин с конструктором сайта и интеграциями WB / Ozon

**Версия:** 1.1 (с учётом решений заказчика от 2026-09-19)
**Кодовая база:** https://github.com/Un1v4rse/ekotoriya, коммит `4f6393f`
**Стек текущий:** Python 3.8+, Flask 2.x, Jinja2, JSON-файлы как хранилище
**Целевой стек:** Python 3.10+, Flask, SQLAlchemy + Alembic (SQLite минимум / PostgreSQL рекомендуется), см. раздел 6

---

## 1. Цель проекта

Полноценный интернет-магазин, который:

1. Автоматически наполняется товарами из личных кабинетов Wildberries и Ozon через Seller API.
2. Позволяет через админ-панель полностью перестроить сайт: создавать/удалять разделы, редактировать любой контент, менять цвета, шрифты, оформление — без участия разработчика.
3. Ведёт базу клиентов автоматически (при регистрации и покупке) и на её основе строит персональные рекомендации товаров на главной странице (по аналогии с Ozon/Wildberries).
4. Имеет встроенный модуль SEO-продвижения, настраиваемый из админки.
5. Позволяет админу выставлять собственную скидку на любой товар поверх цены маркетплейса.
6. Работает без заметных задержек: целевые метрики — раздел 7.

**Вне рамок текущей версии (реализуется позднее):** онлайн-оплата, email/SMS-рассылки, SMS-подтверждение телефона.

### 2.2. Выявленные проблемы и ограничения (обязательны к устранению)

1. **Нет интеграции с Ozon вообще.** Есть только WB.
2. **Хранилище — JSON-файлы** (`content.json`, `wb_products.json`, `customers.json`). Последствия:
   - гонки при конкурентной записи (фоновый поток авто-синка + запросы админки + публичные API) → **потеря данных**;
   - `load_content()` читает и парсит весь `content.json` (сотни КБ–МБ) **на каждый HTTP-запрос** → деградация скорости при росте;
   - нет транзакций, бэкапов, индексов — рост базы клиентов замедлит всё.
3. **Корзина и личный кабинет — заглушки** (`basket_stub`, `personal_stub`). Полноценного ЛК с историей заказов нет.
4. **Рекомендации не персональные**: `get_popular_products()` считает один общий рейтинг для всех. Требование «как Ozon/WB» (на основе истории конкретного клиента) не выполнено.
5. **Заказы не привязываются к аккаунту на сайте**: заказ создаётся по имени+телефону из формы; нет привязки к залогиненному клиенту, нет истории покупок в ЛК.
6. **Скидка админки суммируется со скидкой WB** (`wb_discount + admin_discount`). По решению заказчика (раздел 3, п. 2) семантика меняется: сайт показывает цену маркетплейса, на неё админ накладывает **свою** скидку.
7. **Безопасность:**
   - `/admin/api/upload` — **нет валидации типа/размера файла**, файл сохраняется под исходным именем → риск XSS через `.html`/`.svg`/`.js` и перезаписи файлов;
   - `content_html` выводится через `| safe` — любой, кто получил доступ к админке, может внедрить произвольный JS (приемлемо только при строгой политике доступа + CSP);
   - `proxy_image`: проверка хостов по подстроке `'cdn'` слишком широкая;
   - нет rate-limit на публичные POST (`/api/register`, `/api/order`, `/api/like`) → спам и накрутка лайков/заявок;
   - нет защиты входа в админку (lockout/captcha) от перебора пароля.
8. **Нет тестов** вообще (ни unit, ни e2e). Требование «никаких багов» без автотестов не выполнимо.
9. **Демо-режим включён по умолчанию** при отсутствии токена — в проде риск отдать фейковые товары посетителям.
10. **Одностраничные fallback-заглушки** корзины/ЛК — нарушают требование «редактировать всё что угодно» (эти страницы не в конструкторе).

## 3. Принятые решения по открытым вопросам

| # | Вопрос | Решение заказчика | Следствие для ТЗ |
|---|---|---|---|
| 1 | Интеграция Ozon | Ozon Seller API. Возможность выгружать **все** товары или **выбранные**. Та же возможность — в интеграции WB | Раздел 4.1.4 / 4.2.5: фильтр выгрузки «все / по списку / по категории» для обоих маркетплейсов |
| 2 | Формула скидки | Товар тянется с WB/Ozon со своим ценником; админ выставляет скидку **на своём сайте** | Раздел 4.3: `итоговая_цена = цена_маркетплейса × (1 − скидка_админа / 100)`. Скидка МП показывается как зачёркнутая цена, скидка сайта — отдельной строкой |
| 3 | Оплата | Пока не трогаем, реализуется позже | Заказы оформляются как заявки без оплаты; архитектура не блокирует добавление платежей позже |
| 4 | Вход в ЛК | Регистрация и вход по **телефону + пароль**. SMS-подтверждение не требуется | Раздел 4.9: простая регистрация по телефону и паролю без верификации номера (в будущем — опциональная верификация) |
| 5 | Рассылки | Не требуются на данный момент | Сегменты клиентов остаются в scope (нужны для рекомендаций), модули рассылок не делаем |
| 6 | Сервер | Информации нет, ориентир — «средний» | Раздел 7: VPS среднего класса (4 vCPU / 8 ГБ / SSD 80 ГБ), Docker + docker-compose, gunicorn, PostgreSQL |
| 7 | Нагрузка | Неизвестна, ориентир — «средняя» | Раздел 7: до 10 000 товаров, 50 000 клиентов, 100 заказов/день, пик 20 RPS |

## 4. Функциональные требования

### 4.1. Интеграция с Wildberries (доработка существующего)

- **WB-1.** Синхронизация карточек, цен, скидок, остатков через официальный Seller API (уже есть).
- **WB-2.** Автосинхронизация по расписанию с настройкой периодичности в админке (есть; **добавить**: запуск через cron/планировщик вместо фонового потока при переходе на БД — поток теряет состояние при рестарте и дублирует работу в multi-worker режиме).
- **WB-3.** Демо-режим включается **только явным переключателем в админке**, не автоматически (сейчас — автоматически при отсутствии токена).
- **WB-4.** Журнал синхронизации с фильтрами и уведомлением админу при ошибках.
- **WB-5.** Режим выгрузки товаров (новое): **все товары кабинета** / **выбранные товары** (список nmID с поиском и галочками в админке) / **по категории**. Товары, исключённые из выгрузки, на сайте не показываются и из базы не удаляются (флаг `visible`).

### 4.2. Интеграция с Ozon (новый модуль `ozon_sync.py`, по аналогии с `wb_sync.py`)

- **OZ-1.** Подключение по Ozon Seller API: Client-Id + Api-Key, задаются в админке (`site.ozon_client_id`, `site.ozon_api_key`).
- **OZ-2.** Загрузка товаров: `POST /v3/product/list` + `POST /v3/product/info/list` (карточки), `POST /v5/product/info/prices` (цены), `POST /v4/product/info/stocks` (остатки).
- **OZ-3.** Унификация формата товара — единая схема для обоих источников:

  ```
  {id, source: 'wb'|'ozon', nm_id | offer_id, name, brand, price,
   discount_price, mp_discount_percent, admin_discount_percent,
   photo, url, stock, updated_at, visible}
  ```

  Каталог, карточки, скидки, поиск и рекомендации работают с товарами обоих источников одинаково.
- **OZ-4.** Режим выгрузки (аналог WB-5): **все** / **выбранные** (по списку) / **по категории**.
- **OZ-5.** Автообновление цен/остатков по расписанию (как у WB).
- **OZ-6.** Отдельный журнал синхронизации Ozon; общий экран «Интеграции» в админке с двумя вкладками (WB / Ozon).
- **OZ-7.** Индикатор источника на карточке товара (опционально, настраивается в теме).

### 4.3. Система цен и скидок

- **PR-1.** Товар тянется с маркетплейса с его ценой (`price` — базовая, `discount_price` — со скидкой МП, если МП её даёт).
- **PR-2.** **Формула итоговой цены на сайте** (по решению заказчика):

  ```
  база = discount_price, если задана, иначе price
  итоговая_цена = база × (1 − admin_discount_percent / 100)
  ```

  Скидка маркетплейса и скидка сайта показываются на карточке раздельно: зачёркнутая базовая цена → цена МП → итоговая цена сайта с бейджем «скидка X% на сайте».
- **PR-3.** В админке: индивидуальная скидка на товар (есть), **массовая скидка** по выбранным товарам (есть), скидка **по категории / по всему каталогу / по источнику (WB/Ozon)** (новое).
- **PR-4.** Тип скидки: процент (0–99) **или фиксированная сумма в рублях** (новое; при фикс. сумме `итог = база − сумма`, не ниже 1 руб.).
- **PR-5.** Скидки применяются **только на сайте**. Push скидки обратно в маркетплейсы не делаем (исключено; существующий `wb_push_discounts` вывести из кода или оставить выключенным по умолчанию).
- **PR-6.** Округление итоговой цены — до целых рублей (округление в пользу клиента); зафиксировать в тестах.
- **PR-7.** История изменения скидок: кто, когда, какое значение (аудит-лог).

### 4.4. Каталог и карточки товаров

- **CT-1.** Единый каталог товаров WB + Ozon с фильтрами (цена, категория, наличие, источник), сортировкой (популярность, цена, новизна), пагинацией.
- **CT-2.** Карточка товара: фото (проксирование есть), цены по схеме PR-2, наличие, характеристики из API, Schema.org Product (есть), кнопка «Купить в 1 клик» (есть), кнопка «Нравится» (лайк — есть).
- **CT-3.** Товары без фото → заглушка (есть).
- **CT-4.** Товары с нулевым остатком: скрывать / показывать «нет в наличии» — настройка в админке.
- **CT-5.** Поиск по каталогу (подстрока по названию/бренду/артикулу).

### 4.5. База клиентов (доработка `customers.py`)

- **CL-1.** Клиент создаётся/обновляется автоматически: при регистрации, при оформлении заявки (есть), при заполнении любых форм обратной связи с телефоном.
- **CL-2.** Дедупликация по нормализованному телефону (есть) + по email.
- **CL-3.** Профиль клиента: контакты, история заявок, лайкнутые товары, сумма покупок, дата последней активности.
- **CL-4.** Экспорт базы клиентов в CSV из админки.
- **CL-5.** Сегменты клиентов (правила: «покупал категорию X», «N заявок за период», «не активен 30 дней») — используются для рекомендаций. Модуль рассылок **не делаем**.
- **CL-6.** Чекбокс согласия на обработку ПДн в формах; хранение согласия; удаление клиента по запросу (152-ФЗ).

### 4.6. Рекомендательная система

- **RS-1.** Собираемые события: просмотр карточки, лайк (есть), заявка/заказ (есть), добавление в избранное, поисковые запросы.
- **RS-2.** Два уровня рекомендаций:
  - **Персональные** (для залогиненного клиента — по его истории просмотров/лайков/покупок): «Вам может понравиться», «Похожие товары», «С этим покупают».
  - **Общие** (для анонимов): топ по заказам+лайкам (текущее поведение — оставить как fallback).
- **RS-3.** Взвешивание: заказ > лайк > просмотр (веса настраиваются в админке).
- **RS-4.** Актуальность: свежие события важнее старых (затухание по времени).
- **RS-5.** Рекомендации кэшируются и пересчитываются инкрементально; для холодного старта — fallback на популярное.
- **RS-6.** «Похожие товары»: по общим характеристикам (категория, бренд, ценовой диапазон) + совместная покупаемость.
- **RS-7.** В админке: настройки рекомендаций (веса, количество блоков, включение/выключение секций на главной).

- **LC-4.** Корзина: добавление нескольких товаров, изменение количества, оформление заявкой **без оплаты** (оплата — отдельный будущий этап). Заявка уходит в базу заявок админки.
- **LC-5.** Оформление «в 1 клик» без регистрации — сохраняется (заказ по имени+телефону); если телефон совпал с аккаунтом — заявка привязывается к нему.

## 5. Конструктор: границы гибкости

Чтобы выполнить одновременно «максимально гибкий конструктор» и «всё работает корректно»:

1. Все пользовательские вводы в блоках валидируются на сервере (HEX-цвета, размеры, URL — частично есть; распространить на все поля).
2. Произвольный HTML-блок — только для суперадмина; для остальных ролей — санитайзер разрешённых тегов.
3. Любое изменение темы не ломает вёрстку: валидатор значений перед сохранением, fallback к дефолту (принцип уже реализован в `_css_color`/`_css_size`).
4. Каждый тип блока покрыт автотестами рендеринга.

## 6. Архитектура и миграция хранилища (критично)

Текущая схема «JSON-файлы + перечитывание на каждый запрос» противоречит требованиям «никаких лагов» и «никаких багов» (гонки записи). Обязательные изменения:

- **AR-1.** Миграция на СУБД: PostgreSQL (рекомендуется) или SQLite (минимум). Таблицы: `pages`, `blocks`, `site_settings`, `theme`, `products`, `discounts`, `customers`, `customer_auth`, `orders`, `events` (просмотры/лайки), `recommendations`, `sync_logs`, `admin_users`, `audit_log`.
- **AR-2.** ORM: SQLAlchemy + Alembic (миграции схемы). Скрипт миграции существующих JSON в БД — одноразовый.
- **AR-3.** Кэширование (Flask-Caching, Redis при необходимости): каталог, тема, меню, рекомендации; инвалидация при сохранении. Цель — рендер страницы < 100 мс без кэша, < 20 мс с кэшем.
- **AR-4.** Фоновые задачи: синхронизация WB/Ozon и пересчёт рекомендаций — через cron/планировщик (RQ или простой cron-скрипт), не через поток в процессе веб-сервера.
- **AR-5.** Загрузка файлов: валидация расширения/MIME/размера, уникальные имена, запрет перезаписи.
- **AR-6.** Структурированные логи + алерт админу при падении синка.
- **AR-7.** WSGI-сервер для прода: gunicorn (dev-сервер Flask только для разработки).
- **AR-8.** Деплой: Docker + docker-compose (app, db, nginx); конфигурация через переменные окружения.

## 7. Нефункциональные требования

**Предположения заказчика (сервер «средний», нагрузка «средняя»), приняты как базовые:**

- Сервер: VPS 4 vCPU / 8 ГБ RAM / SSD 80 ГБ, отдельный том под бэкапы.
- Объёмы: до 10 000 товаров, 50 000 клиентов, 100 заказов/день, пик 20 RPS.

**Метрики:**

- TTFB страниц ≤ 300 мс (p95) на проде; LCP ≤ 2,5 с; ответ API ≤ 200 мс (p95).
- Картинки: lazy-loading (есть), WebP, ресайз на лету, кэш прокси-картинок (есть).
- Надёжность: падение маркетплейса/синка не валит сайт (best-effort, принцип уже заложен для остатков); сайт работает на последних данных + пометка «обновлено …».
- Безопасность: закрыть все пункты 2.2.7; CSP-заголовки; rate-limit на публичные POST; lockout входа в админку; HTTPS-only; регулярное обновление зависимостей.
- Совместимость: Python 3.10+, современные браузеры, мобильная адаптивность.
- Резервное копирование: БД + `static/uploads` ежедневно, хранить 14 дней.

## 8. Тестирование и критерии приёмки

- **TS-1.** Unit-тесты: рендер каждого типа блока; `final_price` по формуле PR-2 (округление, границы 0/99%, фикс. сумма); нормализация телефонов; дедупликация клиентов; расчёт рекомендаций.
- **TS-2.** Интеграционные: полный цикл «синк WB/Ozon → карточка → заявка → клиент в базе → рекомендация» (моки API).
- **TS-3.** E2E (Playwright): регистрация по телефону+пароль, вход в ЛК, покупка в 1 клик, лайк → рекомендации изменились, создание страницы в конструкторе, смена темы, выставление скидки.
- **TS-4.** Нагрузочное: 20 RPS на каталог, p95 в рамках раздела 7.
- **TS-5.** CI (GitHub Actions): линтер + тесты на каждый коммит; ручной чек-лист (~50 сценариев) перед релизом.

**Критерии приёмки:**

1. Каталог наполняется из WB и Ozon автоматически по расписанию; режим «все/выбранные» работает в обеих интеграциях; журналы синка без ошибок.
2. Скидка админа корректно считается и отображается на сайте по формуле PR-2 (проверка на 20 товарах вручную + автотесты).
3. Регистрация/вход по телефону+паролю работают; регистрация и покупка добавляют клиента в базу без дублей; в ЛК видна история.
4. Главная показывает персональные рекомендации для залогиненного и популярное для анонима.
5. Новый раздел создаётся в админке без правки кода; тема полностью меняется из админки; корзина и ЛК редактируемы в конструкторе.
6. SEO: sitemap/robots/редиректы/мета редактируются из админки; валидаторы Schema.org проходят.
7. Lighthouse: Performance ≥ 90, SEO ≥ 95.
8. Ни один автотест не падает.
