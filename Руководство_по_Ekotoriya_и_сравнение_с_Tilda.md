# Часть I. Конструктор Ekotoriya

## 1. Назначение и общая архитектура

### 1.1. Что представляет собой конструктор

Ekotoriya позволяет администратору собирать страницы из JSON-описаний блоков, редактировать их непосредственно на реальной странице сайта и публиковать результат без ручного изменения HTML-шаблонов. Поверх этого работают каталог товаров, заказы, личный кабинет, отзывы, заявки, чаты, рекомендации и синхронизация с Wildberries/Ozon.

Это не отдельный внешний сервис и не визуальный редактор, который лишь сохраняет картинку страницы. Конструктор встроен в серверное приложение и использует его реальные данные.

### 1.2. Технологический состав

| Уровень | Реализация |
|---|---|
| Сервер | Python, Flask |
| Шаблоны страниц | Jinja2 |
| База данных | SQLAlchemy; по умолчанию SQLite, через `DATABASE_URL` возможен другой поддерживаемый backend, в документации кода приведён PostgreSQL |
| Модель содержимого | JSON-массивы блоков в полях `Page` |
| Рендер | Python-функции превращают блоки в HTML до выдачи страницы |
| Редактор | Vanilla JavaScript ES2020+, без jQuery и `eval` |
| Адаптивный холст | same-origin iframe с реальной шириной страницы |
| Стили | общая тема `/theme.css`, стили `cb-*`, инлайн-стили отдельных свойств |
| Безопасность | сессии администратора, CSRF, роли, проверка URL и файлов, санитайзинг HTML/CSS |

### 1.3. Как блок превращается в страницу

```text
Администратор
  ↓ выбирает блок и меняет свойства
Массив JavaScript-объектов blocks[]
  ↓ JSON-запрос к серверу
Серверный рендер блоков
  ↓ HTML с классами cb-* и служебными марками редактора
Страница в реальном Jinja2-шаблоне
  ↓ публикация
Page.published_blocks + Page.content_html
  ↓
Публичная страница для посетителей
```

Для редактора сервер дополнительно вставляет комментарии `<!--blk:N-->` и `<!--/blk-->`. Они обозначают границы каждого блока в уже готовом DOM. Благодаря этому редактор знает, какой реальный фрагмент страницы соответствует какому JSON-объекту, и может показывать рамку, панель операций и обрабатывать двойной клик.

### 1.4. Серверный рендер вместо полностью клиентского

Содержимое обычных блоков формируется на сервере. Это даёт несколько практических последствий:

- один и тот же рендер используется для редактора, предпросмотра и публичной страницы;
- текстовые значения экранируются при генерации HTML;
- карточки товаров получают актуальные серверные данные;
- ограничения свойств проверяются не только визуальной панелью, но и серверным кодом;
- дополнительные скрипты подключаются условно: например, код таймера добавляется только при наличии блока `timer`, а код анимаций — только если какой-либо блок использует эффекты.

## 2. Страницы и модель данных

### 2.1. Основные сущности

```text
Сайт
├── Общие настройки SiteSetting
│   ├── site / menu / socials
│   ├── тема и её история
│   └── глобальные Header / Footer
├── Страницы Page
│   ├── рабочие и опубликованные блоки
│   ├── черновик
│   ├── SEO- и Open Graph-настройки
│   └── версии PageVersion
├── Мои блоки BlockTemplate
├── Товары Product
├── Заказы, клиенты, заявки, отзывы и чаты
└── Администраторы AdminUser и журнал AuditLog
```

### 2.2. Поля страницы

| Поле | Назначение |
|---|---|
| `slug` | Внутренний уникальный идентификатор страницы |
| `url` | Публичный адрес |
| `title`, `h1` | Название документа и основной заголовок |
| `meta_description`, `meta_keywords`, `canonical` | SEO-поля |
| `template` | Jinja2-шаблон, внутри которого выводится содержимое |
| `blocks` | Рабочий массив блоков, совместимый со старой моделью сохранения |
| `draft_blocks` | Черновик с массивом блоков и временем сохранения |
| `published_blocks` | Последний опубликованный массив |
| `content_html` | Производный HTML, который выводится посетителям |
| `settings` | Open Graph, favicon, цвета страницы, собственный код и переопределения зон |
| `updated_at` | Метка изменения, также участвующая в обнаружении конфликтов |

### 2.3. Черновик и опубликованная версия

В актуальном редакторе автосохранение пишет только `draft_blocks` и не меняет публичный HTML. При публикации выполняется последовательность:

1. текущий черновик сохраняется;
2. `/admin/api/page-save` записывает блоки и мета-поля, проверяя `expected_updated_at`;
3. `/admin/api/page-publish` копирует черновик в `published_blocks`;
4. заново формируется `content_html`;
5. автоматически создаётся снапшот версии с меткой «Авто»;
6. сбрасывается кэш сайта.

Поэтому в пользовательском сценарии **«Сохранить черновик» и «Опубликовать» — разные действия**.

### 2.4. Системные страницы

Корзина, личный кабинет, авторизация и страница 404 защищены от удаления. На системных страницах конструкторские блоки выводятся над их функциональным содержимым. Например, над корзиной можно разместить информационный заголовок или баннер, не заменяя саму корзину.

Обычные страницы открываются в редакторе через iframe-обёртку. Для системных страниц сохранён старый инлайн-режим редактора.

## 3. Интерфейс редактора

### 3.1. Три рабочие зоны

| Зона | Содержимое |
|---|---|
| Верхняя панель | Навигация, история, сохранение, устройства, масштаб, настройки, версии, предпросмотр и публикация |
| Левая панель | Библиотека блоков, «Мои блоки», структура текущей страницы |
| Центральный холст | Реальная страница сайта с рамками выделения и инлайн-редактированием |
| Правая панель | Свойства выбранного блока: контент, фон, расположение, типографика, кнопка, эффекты и дополнительные параметры |

Боковые панели можно сворачивать. На узком экране правая панель работает как оверлей. Отдельный режим скрывает редакторский интерфейс для чистого просмотра страницы; `Esc` возвращает панели.

### 3.2. Верхняя панель

Доступны следующие группы действий:

- возврат в административную панель;
- отмена и повтор;
- индикатор состояния сохранения;
- переключатели **Desktop / Tablet / Mobile**;
- масштаб 50–100%, автоматическое размещение по ширине и полноширинный режим;
- справка по горячим клавишам;
- настройки страницы;
- версии;
- предпросмотр;
- скрытие интерфейса;
- статус «Черновик» или «Опубликовано»;
- ручное сохранение черновика;
- публикация;
- выход.

### 3.3. Устройства и масштаб

| Режим | Ширина содержимого |
|---|---:|
| Desktop | 1200 px |
| Tablet | 768 px |
| Mobile | 360 px |

Это не просто уменьшение внешней картинки. Для обычных страниц реальный сайт загружается в same-origin iframe указанной ширины, поэтому CSS media queries срабатывают так же, как на соответствующем экране. Масштаб влияет только на отображение рабочей области и не подменяет ширину самой страницы.

`Ctrl` + колесо мыши меняет масштаб. Режим «Во всю ширину» убирает масштабирование и использует доступную область редактора.

## 4. Добавление и редактирование блоков

### 4.1. Способы добавления

1. Открыть категорию в левой библиотеке.
2. Выбрать тип и, если есть, визуальный пресет.
3. Перетащить карточку в нужное место страницы либо активировать вставку кликом.
4. Также можно навести указатель на блок и использовать появляющуюся кнопку добавления под ним.
5. После вставки заполнить вкладку «Контент» и настроить оформление.

Пресет — это начальный JSON-объект с заранее заданными значениями. Например, у заголовка есть H1 по центру, H2 слева и H3 слева; у баннера — брендовый, тёмный и светлый варианты.

### 4.2. Операции с блоком

Панель выбранного блока позволяет:

- перетаскивать блок за специальную ручку;
- перемещать на одну позицию вверх или вниз;
- дублировать;
- сохранить в «Мои блоки»;
- скрыть без удаления;
- открыть Zero-редактор для блока `zero`;
- удалить.

Структура страницы в левой панели повторяет порядок блоков и позволяет выбирать их. Скрытые блоки остаются в структуре.

### 4.3. Инлайн-редактирование

- Один клик выделяет блок.
- Двойной клик по поддерживаемому тексту включает `contenteditable`.
- Двойной клик по изображению в блоках «Картинка», «Галерея» и «Текст + фото» открывает выбор изображения.
- Панель инлайн-правки предлагает жирный, курсив, ссылку и завершение редактирования.
- `Esc` завершает правку.

**Важная особенность:** у обычных блоков результат сериализуется как plain text. Поэтому визуально применённые жирный, курсив и ссылка не становятся постоянной Rich Text-разметкой такого блока. Для секций перенесённого дизайна сохраняется HTML, и там форматирование имеет другой путь сохранения. Для обычных блоков оформление следует задавать через типографику и свойства, а не рассчитывать на полноценный визуальный редактор форматированного текста.

### 4.4. История изменений

Undo/redo хранит до 50 состояний массива блоков. Изменения свойств и операции с блоками записываются в историю; для частых правок используется короткая задержка, чтобы не создавать состояние на каждый промежуточный шаг.

Горячие клавиши:

| Клавиши | Действие |
|---|---|
| `Ctrl/Cmd + S` | Сохранить черновик |
| `Ctrl/Cmd + Z` | Отменить |
| `Ctrl/Cmd + Shift + Z`, `Ctrl/Cmd + Y` | Повторить |
| `Delete`, `Backspace` | Удалить выбранный блок, если фокус не в поле ввода |
| `Esc` | Завершить правку, закрыть панель или снять выделение |
| `?` | Показать справку |
| `Ctrl/Cmd + колесо` | Изменить масштаб |

## 5. Библиотека: категории и типы

В библиотеке 18 категорий. Они группируют 23 технических типа блоков; некоторые типы дополнительно имеют несколько пресетов.

| Категория | Типы блоков |
|---|---|
| Секции сайта | `section` — секция перенесённого дизайна |
| Обложка | `banner`, `text_image` |
| Заголовки | `heading` |
| Текст | `text`, `text_columns` |
| Изображения | `image`, `gallery` |
| Товары | `products` |
| Тарифы и цены | `table` |
| Формы | `form`, `contacts` |
| Отзывы | `reviews` |
| FAQ | `faq` |
| Карта | `map` |
| Кнопка | `button` |
| Видео | `video` |
| Преимущества | `features` |
| Разделитель | `divider`, `spacer` |
| Таймер | `timer` |
| Zero | `zero` |
| HTML | `html` |

Здесь важно не сравнивать напрямую «23» с числом стандартных блоков Tilda. В Ekotoriya тип — отдельная программная сущность со своим рендером и полями. В Tilda сотни готовых блоков во многом являются разными дизайн-композициями сходных сущностей.

## 6. Все 23 типа блоков и их свойства

Для каждого блока ниже перечислены собственные поля вкладки «Контент». Общие настройки фона, отступов, типографики, эффектов и CSS разобраны отдельно в следующем разделе.

### 6.1. `heading` — заголовок

**Назначение:** самостоятельный заголовок страницы или раздела.

| Свойство | Возможные значения и поведение |
|---|---|
| `text` | Текст заголовка |
| `level` | `h1`, `h2` или `h3`; неизвестное значение заменяется на `h2` |
| `align` | Слева, по центру или справа |

Текст доступен для инлайн-правки. Типографика области `title` позволяет отдельно менять шрифт, размер, цвет и другие параметры. Сервер экранирует текст.

### 6.2. `text` — текст

**Назначение:** абзацы и пояснения.

- `text` — основной текст;
- `align` — выравнивание слева, по центру или справа;
- пустая строка в поле разделяет абзацы;
- одиночный перевод строки внутри абзаца превращается в `<br>`;
- пустой блок не выводится.

Двойной клик позволяет править текст на холсте. Это не Rich Text-поле уровня Tilda: постоянное форматирование отдельных слов обычным блоком не сохраняется.

### 6.3. `text_image` — текст с изображением

**Назначение:** двухколоночная секция «о компании», «о продукте» или «преимущество».

| Свойство | Назначение |
|---|---|
| `title` | Заголовок секции |
| `text` | Абзацы текста |
| `src` | URL изображения из медиатеки или внешнего источника |
| `alt` | Альтернативный текст; если пуст, сервер использует заголовок |
| `image_pos` | Изображение слева или справа |

На широком экране используются две равные колонки, при ширине до 767 px сетка становится одноколоночной. Заголовок, текст и изображение можно менять на холсте.

### 6.4. `image` — одиночное изображение

| Свойство | Назначение |
|---|---|
| `src` | Адрес изображения |
| `alt` | Текст для доступности и поисковых систем |
| `caption` | Необязательная подпись под изображением |
| `align` | Размещение слева, по центру или справа |
| `width` | Ширина в `px`, `%`, `rem` или `em`; значение проходит серверную проверку формата |

Изображение загружается лениво. Если адрес ещё не задан, выводится заметная заглушка `noimage`, поэтому блок не исчезает с холста и его можно выбрать.

### 6.5. `gallery` — галерея

- `title` — необязательный заголовок;
- `cols` — интерфейс предлагает 2, 3 или 4 изображения в ряд;
- `items[]` — список фотографий;
- `items[].src` — адрес файла;
- `items[].alt` — альтернативный текст.

Фотографии можно добавлять из медиатеки, удалять и переставлять. Пустая галерея получает три заглушки, сохраняя блок доступным для редактирования. Изображения выводятся в адаптивной сетке и лениво загружаются.

> В исследованном commit обнаружена техническая нестыковка: значение `cols` проверяется сервером, но соответствующий класс `cb-gallery-c2/c3/c4` не попадает в итоговую разметку. Поэтому переключатель числа колонок в этой версии может не влиять на фактическую сетку. Подробнее — в разделе ограничений.

### 6.6. `products` — товары

**Назначение:** вставка реальной товарной витрины в произвольную страницу.

| Свойство | Возможные значения |
|---|---|
| `title` | Заголовок подборки |
| `mode` | `source` — по источнику, `category` — по категории, `recommendations` — рекомендации |
| `source` | `all`, `wb` или `ozon` |
| `category` | Строка категории для режима `category` |
| `limit` | От 1 до 48 товаров; по умолчанию 8 |

Блок не хранит самостоятельные карточки с вручную введёнными ценами. Сервер берёт видимые записи `Product`, применяет ценообразование и скидки сайта, после чего формирует карточки. В них доступны фотография, название, итоговая цена, признак скидки, состояние остатка, избранное и покупка в один клик. При нулевом остатке покупка отключается.

Это одно из главных отличий от универсального блока товаров: конструктор напрямую связан с каталогом, остатками и коммерческой логикой приложения.

### 6.7. `table` — таблица

- `title` — заголовок;
- `header_row` — использовать первую строку как шапку;
- `items[]` — строки;
- `cells` — массив ячеек либо строка с разделителем `|`.

Пример заполнения строки: `Размер | 160×200 | 2 601 ₽`. Таблица помещается в контейнер с горизонтальной прокруткой, что помогает на узком экране. Содержимое ячеек экранируется.

### 6.8. `form` — форма связи

| Свойство | Назначение |
|---|---|
| `title` | Заголовок формы |
| `button` | Подпись кнопки отправки |
| `recipient` | Необязательный контакт, добавляемый в служебное описание заявки |

Состав полей фиксирован:

- имя — обязательно;
- телефон — обязательно;
- email — необязательно;
- согласие на обработку персональных данных — обязательно.

Форма отправляется на `/api/order`; заявка попадает в раздел клиентов и заявок админки. Поле `recipient` не является самостоятельной настройкой почтовой интеграции: оно включается в примечание к заявке. В конструкторе нет редактора произвольных полей, многошаговых форм, условий, калькулятора или квизов.

### 6.9. `contacts` — контактная карточка

Поля:

- `title`;
- `phone` — превращается в ссылку `tel:`;
- `email` — превращается в ссылку `mailto:`;
- `address`;
- `worktime`.

Пустые поля не выводятся. Это содержательный блок контактов, а не карта и не форма.

### 6.10. `reviews` — отзывы

- `title` — общий заголовок;
- `items[].name` — имя автора, по умолчанию «Покупатель»;
- `items[].text` — текст отзыва;
- `items[].rating` — оценка от 1 до 5.

Оценка выводится звёздами, а карточки размещаются в адаптивной сетке. Этот блок содержит **ручной список отзывов**. Он не следует путать с отдельной моделью `Review`, где отзывы пользователей проходят модерацию: автоматической подгрузки модерированных записей в данный тип блока в коде нет.

### 6.11. `faq` — вопросы и ответы

- `title` — заголовок;
- `items[].q` — вопрос;
- `items[].a` — ответ.

Каждый пункт рендерится через нативные `<details>` и `<summary>`, то есть работает как аккордеон без обязательного JavaScript. Неполные пункты без вопроса или ответа пропускаются. Если список пуст, выводится заглушка с приглашением добавить вопросы.

### 6.12. `map` — карта

- `title` — заголовок;
- `address` — адрес или координаты;
- `zoom` — масштаб от 9 до 18, по умолчанию 16.

Сервер формирует embed Яндекс.Карты по адресу. Высота iframe в общих стилях — 420 px. Без адреса блок не выводится.

### 6.13. `button` — кнопка с действием

Основные поля: `text`, `align` и параметры выбранного действия. Поддерживаются семь действий:

| `action` | Дополнительные поля | Результат |
|---|---|---|
| `link` | `url` | Обычная ссылка |
| `anchor` | `anchor` | Переход к `#якорю`; идентификатор очищается от лишних символов |
| `tel` | `phone` | Звонок через `tel:` |
| `mailto` | `email` | Письмо через `mailto:` |
| `form` | — | Открытие всплывающей формы заявки общим скриптом сайта |
| `subscribe` | — | Открытие формы подписки |
| `popup` | `popup_title`, `popup_text` | Текстовый попап; содержимое экранируется |

Кнопка поддерживает общий набор стилей: заливка, обводка или вариант без фона, цвета, радиус, тень, размер и hover-эффект. Неизвестное действие сервер заменяет обычной ссылкой.

### 6.14. `video` — видео

Единственное собственное поле — `url`. Обычный блок поддерживает ссылки YouTube и Vimeo и выводит плеер в контейнере с соотношением сторон 16:9. Для пустой или неподдерживаемой ссылки показывается заглушка.

Видео в фоне блока и видео внутри Zero-блока дополнительно поддерживают RuTube. Это расширение не относится к обычному блоку `video`.

### 6.15. `features` — преимущества

- `title` — заголовок секции;
- `cols` — интерфейс предлагает 2–5 колонок;
- `items[].icon` — иконка;
- `items[].title` — название преимущества;
- `items[].text` — описание.

Поле иконки принимает три формы:

1. `icon:имя` — одна из 19 встроенных SVG-иконок;
2. URL загруженного изображения;
3. короткий текст или эмодзи.

Встроенный набор: `truck`, `shield`, `percent`, `chat`, `star`, `heart`, `phone`, `mail`, `check`, `arrow-right`, `box`, `gift`, `clock`, `map-pin`, `wallet`, `award`, `refresh`, `factory`, `leaf`. SVG использует `currentColor` и наследует цвет элемента.

Как и у галереи, в текущем commit значение `cols` валидируется, но нужный класс колонок не выводится серверным рендером.

### 6.16. `divider` — разделитель

Собственных полей нет. Выводится тонкая горизонтальная линия с заданными в CSS отступами. При необходимости к блоку применяются общие фон, отступы, видимость и эффекты.

### 6.17. `spacer` — вертикальный отступ

Поле `height` задаёт высоту в пикселях, по умолчанию 40. Сервер принимает числовое значение длиной до трёх цифр. Это простой способ увеличить расстояние между секциями, хотя у остальных блоков также есть вертикальные padding-настройки.

### 6.18. `text_columns` — текст в колонках

- `title` — заголовок;
- `items[].text` — содержимое каждой колонки.

Предполагается от двух до четырёх колонок, абзацы обрабатываются так же, как в обычном текстовом блоке. В текущей версии сервер рассчитывает число колонок, но не передаёт рассчитанный модификатор в HTML, поэтому поведение переключения сетки требует доработки.

### 6.19. `timer` — таймер акции

| Свойство | Назначение |
|---|---|
| `title` | Заголовок |
| `date` | Дата и, при необходимости, время окончания в ISO-совместимом формате |
| `button_text` | Необязательная кнопка |
| `button_link` | Ссылка кнопки |

JavaScript обновляет отсчёт каждую секунду в формате дней, часов, минут и секунд. После наступления даты выводится «Акция завершена», при некорректной дате — просьба указать дату. Гидратор подключается на страницу только при наличии таймера.

### 6.20. `zero` — свободная композиция

Собственные поля верхнего уровня:

- `height` — высота холста от 100 до 2000 px, по умолчанию 500;
- `elements[]` — шесть возможных типов абсолютно позиционированных элементов;
- `responsive` — переопределения для планшета и телефона.

Zero-блок подробно разобран в разделе 8.

### 6.21. `html` — собственный HTML

Поле `html` содержит разметку. Блок доступен только суперадминистратору:

- контент-администратор не может сохранить такой блок — сервер удаляет его из массива;
- при рендере для не-суперадмина возвращается служебный комментарий;
- даже HTML суперадмина проходит санитайзер.

Разрешены ограниченные текстовые и структурные теги: ссылки, выделение, абзацы, списки, `div`, `span`, заголовки и изображения. `script`, `style`, `iframe`, `object` и `embed` удаляются вместе с содержимым; обработчики `on*` и опасные URL также вырезаются.

Следовательно, это **не аналог неограниченного HTML T123**, через который можно вставить любой сторонний JS-виджет.

### 6.22. `section` — секция перенесённого дизайна

**Назначение:** сохранить и повторно использовать готовый фрагмент оригинального сайта Ekotoriya.

| Свойство | Назначение |
|---|---|
| `name` | Название для структуры страницы |
| `html` | Готовая разметка секции |
| `bg` | Необязательный цвет фона |
| `padding` | Общий вертикальный отступ |
| `text_color` | Необязательный цвет текста |

Секция редактируется как единый фрагмент: двойной клик по конкретному заголовку, абзацу или другому поддерживаемому текстовому элементу меняет его внутри HTML. Название может определяться автоматически по известным CSS-классам или первому заголовку.

В отличие от `html`, серверный рендер `section` не пропускает разметку через общий санитайзер. Этот тип рассчитан на доверенный перенесённый контент, а не на вставку непроверенного кода обычным редактором.

### 6.23. `banner` — промо-баннер

- `title` — обязательный для вывода заголовок;
- `subtitle` — подзаголовок;
- `button` и `url` — необязательная кнопка;
- `bg` — цвет фона;
- `text_color` — цвет текста;
- `image` — фоновая фотография;
- `height` — необязательная минимальная высота.

При наличии изображения поверх него добавляется затемнение, а цвет остаётся подложкой. У баннера собственный внутренний контейнер: его фон и высота обрабатываются иначе, чем у обычных блоков. Типографика доступна для заголовка и подзаголовка, стили кнопки — через общий объект `button_style`.

## 7. Общие настройки оформления

### 7.1. Фон

| Параметр | Возможные значения |
|---|---|
| `bg_type` | Наследуемый/по умолчанию, `color`, `image`, `gradient`, `video`, `none` |
| `bg` | Цвет в HEX |
| `bg_image` | Изображение из медиатеки или URL |
| `bg_image_position` | Девять стандартных позиций от `left top` до `right bottom` |
| `bg_image_size` | `cover`, `contain`, `auto` |
| `bg_image_repeat` | `repeat`, `no-repeat` |
| `bg_parallax` | Фиксированный фон через `background-attachment: fixed` |
| `bg_gradient_from`, `bg_gradient_to` | Два цвета градиента |
| `bg_gradient_angle` | Угол 0–360°, по умолчанию 180° |
| `bg_video` | YouTube, Vimeo или RuTube |
| `bg_opacity` | Затемнение видеофона 0–100%, по умолчанию 40% |

Видеофон размещается абсолютным слоем под содержимым. Опасные и неподдерживаемые URL отбрасываются сервером.

### 7.2. Расположение и размеры

- `padding_top`, `padding_bottom` — независимые отступы от 0 до 200 px;
- старое поле `padding` поддерживается для совместимости;
- `min_height` — минимальная высота блока от 0 до 1200 px;
- `content_align` — выравнивание содержимого, если у блока нет собственного `align`;
- `container: theme` — обычная ширина темы;
- `container: full` — растягивание внутреннего контейнера на всю ширину;
- `hidden` — скрытие блока без удаления.

### 7.3. Типографика

Настройки хранятся в `typography` и применяются к областям:

- `title`;
- `subtitle`;
- `text`;
- `caption`;
- `button`;
- `item_title`;
- `item_text`.

Не каждая область существует у каждого блока: например, у изображения есть подпись, а у преимуществ — заголовки и тексты пунктов.

| Свойство | Ограничения серверного рендера |
|---|---|
| `font` | Семейство/CSS-значение длиной до 100 символов без опасных разделителей |
| `font_google` | Только семейство из белого списка конструктора |
| `size` | `px` или `rem`, числовая часть от 8 до 120 |
| `color` | HEX-цвет |
| `line_height` | От 0,8 до 3 |
| `letter_spacing` | `px` или `em`, от −5 до 20 |
| `weight` | normal, medium, bold или число 100–900 |
| `italic` | Курсив |
| `uppercase` | Верхний регистр |
| `align` | left, center, right, justify |

В белом списке блочной типографики 30 Google Fonts. Google Fonts подключаются только для семейств, реально встретившихся в блоках страницы. У общей темы сайта есть отдельный курируемый список шрифтов с кириллицей.

### 7.4. Стили кнопок

Объект `button_style` применяется к блоку кнопки и поддерживаемым кнопкам формы, баннера, таймера и Zero-элементов.

| Свойство | Значения |
|---|---|
| `variant` | `fill`, `outline`, `none` |
| `bg`, `color`, `border_color` | Цвета фона, текста и границы |
| `radius` | 0–60 px, по умолчанию 6 |
| `shadow` | 0 — нет, 1 — небольшая, 2 — выраженная |
| `size` | `s`, `m`, `l` |
| `hover` | `darken` — затемнение, `lift` — подъём, `none` |

### 7.5. Эффекты

Объект `effects` содержит:

- `anim`: `fade`, `slide-up`, `slide-left`, `slide-right`, `zoom`;
- `anim_duration`: 200–2000 мс, по умолчанию 600;
- `anim_delay`: 0–2000 мс;
- `sticky`: закрепление блока вверху;
- `hide_on`: скрытие на мобильных или десктопе;
- `decor_top`, `decor_bottom`: декоративные линии с цветом, толщиной 1–20 px и шириной 1–100%.

Появление реализовано через CSS-переходы и `IntersectionObserver`. Это базовые анимации блока целиком, а не покадровая анимация отдельных элементов.

### 7.6. Дополнительные CSS-настройки

- `css_class` — до 60 символов: латиница, цифры, пробелы, `_` и `-`;
- `custom_css` — только суперадминистратор, максимум 2000 символов;
- CSS применяется в области сгенерированного класса конкретного блока;
- запрещены `@import`, `url(`, `expression(`, `behavior`, `<` и `>`.

## 8. Zero-блок и его элементы

### 8.1. Модель композиции

Zero-блок — это контейнер фиксированной высоты с абсолютно позиционированными элементами. Координаты и размеры хранятся в процентах:

| Поле | CSS-свойство |
|---|---|
| `x` | `left`, % ширины контейнера |
| `y` | `top`, % высоты контейнера |
| `w` | `width`, % |
| `h` | `height`, % |

Дополнительно элемент имеет `rotate`, `z`, `opacity`, `hidden`, необязательный общий `link` и собственный объект `props`.

Процентная модель позволяет масштабировать композицию вместе с контейнером, но не заменяет полноценную адаптивную раскладку: для планшета и телефона нужно проверять расположение вручную.

### 8.2. Работа в Zero-редакторе

Zero-редактор открывается из панели выбранного блока. Плавающая панель содержит:

- кнопки добавления шести типов элементов;
- список слоёв;
- свойства выбранного элемента;
- текущий режим Desktop/Tablet/Mobile;
- закрытие редактора.

Доступные манипуляции:

- перемещение мышью;
- изменение размера за четыре угловые ручки;
- сохранение пропорций при resize с `Shift`;
- поворот отдельной ручкой над элементом;
- перемещение стрелками на 1%;
- точное перемещение с `Alt` на 0,1%;
- изменение ширины или высоты через `Shift` + стрелки;
- блокировка элемента от перетаскивания на время редактирования;
- скрытие, удаление и изменение z-index из списка слоёв.

### 8.3. Текст — `text`

Свойства:

- `props.text` — содержимое;
- `props.text_style` — настройки типографики;
- в панели вынесены цвет и размер шрифта, сервер поддерживает и остальные общие параметры `text_style`.

Текст экранируется. Контейнер ограничивает содержимое своей шириной и высотой с `overflow: hidden`, поэтому слишком большой текст может обрезаться.

### 8.4. Кнопка — `button`

- `props.text`;
- `props.url`;
- `props.button_style`;
- в панели доступны вариант стиля и цвет, сервер поддерживает полный набор кнопочных свойств.

В отличие от самостоятельного блока `button`, Zero-кнопка использует обычную ссылку и не имеет семи действий `form`, `subscribe`, `popup` и других.

### 8.5. Изображение — `image`

- `props.src` — адрес из медиатеки или URL;
- `props.alt`;
- `props.radius` — скругление 0–60 px.

Изображение заполняет элемент и использует `object-fit: cover`. Это удобно для композиции, но важно контролировать обрезку фотографии. Без корректного `src` элемент не рендерится.

### 8.6. Фигура — `shape`

- `props.color`;
- `props.shape`: `rect`, `circle`, `line`.

Фигура заполняет заданный прямоугольник элемента. Для круга нужно самостоятельно следить за пропорциями, для линии — за достаточной высотой.

### 8.7. Видео — `video`

Поле `props.url` поддерживает YouTube, Vimeo и RuTube. Видео занимает весь элемент через iframe. Неподдерживаемая ссылка приводит к пропуску элемента при серверном рендере.

### 8.8. Иконка — `icon`

- `props.icon` — `icon:имя` из встроенного набора либо короткий символ/эмодзи;
- `props.color`;
- `props.size` — от 4 до 200 в логике Zero-рендера.

Встроенные SVG центрируются и наследуют заданный цвет. Произвольный HTML в поле иконки не выводится.

### 8.9. Общие свойства элемента

| Свойство | Назначение |
|---|---|
| `link` | Ссылка на весь элемент, кроме кнопки со своей ссылкой |
| `opacity` | Прозрачность; панель предлагает 10–100% |
| `z` | Порядок наложения 0–100 |
| `rotate` | Поворот от −180° до 180° в серверном рендере |
| `hidden` | Полное скрытие элемента |

### 8.10. Адаптивные переопределения

Desktop — базовая композиция. Для Tablet и Mobile создаются записи:

```text
responsive.tablet[element_id] = {x, y, w, h}
responsive.mobile[element_id] = {x, y, w, h}
```

Пока переопределения нет, элемент наследует координаты Desktop. После перемещения или resize в соответствующем режиме появляется собственный набор координат. Кнопка «Наследовать от desktop» удаляет его.

На публичной странице переопределения превращаются в media queries:

- Tablet — `max-width: 1024px`;
- Mobile — `max-width: 640px`.

Сервер также поддерживает `hide` для отдельного адаптивного правила. Основной UI Zero-редактора сосредоточен на координатах и размерах, а не на полном наборе независимых мобильных стилей.

## 9. Адаптивность и предпросмотр

Адаптивность реализована на нескольких уровнях:

1. **Просмотр реальной страницы в iframe.** Переключатели Desktop, Tablet и Mobile задают ширину фрейма 1200, 768 и 360 px. Это не декоративная уменьшенная копия: внутри работают те же CSS media queries и скрипты, что у посетителя.
2. **Общие стили блоков.** Двухколоночные композиции переходят в одну колонку, галереи и сетки перестраиваются, таблица получает горизонтальную прокрутку.
3. **Скрытие блоков.** Общий эффект `hide_on` позволяет показать разные варианты секции на мобильном и десктопе.
4. **Zero-блок.** Для планшета и телефона можно задать отдельные x/y/w/h каждого элемента.
5. **Проверка предпросмотра.** Перед публикацией черновик сохраняется, а отдельный preview открывает его без изменения публичной версии.

Ограничения по сравнению со зрелым адаптивным конструктором:

- в верхней панели нет свободного ввода произвольной ширины устройства;
- у Zero-блока только два дополнительных диапазона, а не пять стандартных и пользовательские брейкпоинты Tilda;
- переключение устройства не запускает универсальное инлайн-редактирование любой мобильной типографики — изменения зависят от конкретного блока;
- для обычных блоков нет отдельных мобильных padding, font size и других per-breakpoint-настроек.

## 10. Медиатека и работа с изображениями

### 10.1. Источники изображений

Поля изображений принимают URL или файл из медиатеки. Файл можно:

- загрузить через общую медиатеку;
- выбрать повторно в другом блоке;
- вставить в одиночное изображение, галерею, Zero-блок, текст с изображением или фон;
- использовать как OG-изображение страницы, если размеры и содержание подходят.

API медиатеки позволяет получать список файлов и удалять ненужные изображения. Для загрузок установлен лимит 10 МБ. Проверяются разрешённые расширения, MIME-тип и сигнатуры файлов, а не только имя, переданное браузером.

### 10.2. Редактирование изображения в блоке

Конструктор позволяет заменить файл и настроить `alt`, подпись, ширину или позицию. Для фона доступны position, size, repeat и parallax. Однако встроенного растрового редактора с кадрированием произвольной области, фильтрами и ретушью нет: подготовку изображения лучше выполнять заранее.

### 10.3. Доступность и производительность

- обычные изображения и галерея используют ленивую загрузку;
- `alt` следует заполнять осмысленно, особенно для содержательных фотографий;
- для декоративных фоновых изображений текстовой альтернативы нет, поэтому смысл нужно дублировать в контенте;
- исходный размер файла остаётся ответственностью редактора — медиатека не заменяет полноценный CDN с автоматическим набором современных форматов и размеров.

## 11. Повторное использование контента

### 11.1. «Мои блоки» — `BlockTemplate`

Любой настроенный блок можно сохранить как собственный шаблон:

1. выделить блок;
2. вызвать сохранение в «Мои блоки»;
3. задать понятное имя;
4. добавлять его из соответствующей вкладки библиотеки на эту или другую страницу.

Шаблон хранится в базе данных и содержит снимок JSON-блока. При вставке создаётся новый экземпляр: последующее изменение вставленного блока не меняет исходный шаблон и другие копии. Это не синхронизируемый глобальный компонент.

### 11.2. Секции перенесённого дизайна

Отдельная библиотека содержит секции исходного фирменного дизайна: баннеры, преимущества, промо, каталог, бренды, отзывы, карту, товарные подборки, лукбук, истории, услуги, галереи, видео и другие фрагменты. Они вставляются как тип `section`, сохраняя готовую HTML-композицию.

Генератор `build_section_presets.py` извлекает секции из `data/content.json` и формирует `data/section_presets.json`. Следовательно, набор зависит от содержимого локальных данных, а не является полностью зашитым в Git-репозиторий списком.

### 11.3. Готовые шаблоны страниц

При создании новой страницы доступны три начальных сценария:

| Шаблон | Типовое назначение |
|---|---|
| «Лендинг» | Посадочная страница с последовательным рассказом и призывом к действию |
| «Витрина» | Страница с товарной подачей и коммерческими блоками |
| «Контакты» | Контактные данные, карта и связанные секции |

Шаблон ускоряет старт, но не связывает страницу с мастер-шаблоном: после создания блоки редактируются независимо.

### 11.4. Глобальные Header и Footer

Верхняя и нижняя зоны сайта настраиваются централизованно и по умолчанию используются на страницах. Это позволяет менять навигацию и контакты без правки каждой страницы. Для отдельной страницы можно включить переопределение конфигурации.

## 12. Черновики, публикация и версии

### 12.1. Три состояния контента

| Состояние | Поле | Кто видит |
|---|---|---|
| Рабочее | `Page.blocks` | Внутренняя модель страницы |
| Черновик | `Page.draft_blocks` | Редактор и предпросмотр |
| Опубликованное | `Page.published_blocks` + производный `content_html` | Посетители сайта |

После редактирования JavaScript помечает состояние как изменённое. Автосохранение запускается примерно через 5 секунд после последнего изменения; дополнительно предусмотрена периодическая проверка каждые 30 секунд. Ручное сохранение черновика также доступно.

### 12.2. Что происходит при публикации

Упрощённая последовательность:

1. редактор принудительно сохраняет текущий черновик;
2. `/admin/api/page-save` сохраняет метаданные и блоки, передавая `expected_updated_at`;
3. при совпадении версии `/admin/api/page-publish` формирует опубликованные блоки и HTML;
4. сервер создаёт автоматический снапшот версии;
5. посетители начинают получать новый `content_html`.

Черновик и публикация разделены: изменение в редакторе само по себе не должно мгновенно менять публичную страницу.

### 12.3. Конфликт одновременного редактирования

Если с момента загрузки редактора страницу изменил кто-то другой, `page-save` возвращает HTTP 409. Интерфейс сообщает о конфликте и запрашивает подтверждение перезаписи.

Важно: это защита этапа сохранения/публикации, а не полноценная совместная работа в реальном времени. Автосохранение `page-draft` само по себе такой проверки не выполняет, поэтому два редактора всё же могут перезаписать черновики друг друга. Нет presence-индикаторов, курсоров соавторов и объединения изменений.

### 12.4. Версии

- для каждой страницы хранится до 10 снапшотов;
- можно вручную сохранить именованную версию;
- публикация создаёт автоматическую версию;
- список версий доступен из редактора;
- восстановление помещает выбранный снимок в **черновик**;
- восстановленная версия становится публичной только после отдельной публикации.

Это безопасный сценарий: откат можно сначала проверить. Но лимит в 10 версий означает, что долгосрочную историю и сравнение произвольных ревизий он не заменяет.

## 13. Страницы, SEO и настройки сайта

### 13.1. Операции со страницами

Из админки можно:

- создать страницу по шаблону;
- задать slug, title, H1 и meta-поля;
- дублировать существующую страницу;
- удалять обычные страницы;
- открывать редактор и предпросмотр;
- настраивать публикацию и версии.

Системные страницы защищены от удаления и некоторых опасных операций, поскольку на них завязаны маршруты магазина и служебные сценарии.

### 13.2. Настройки конкретной страницы

`Page.settings` поддерживает:

| Настройка | Назначение |
|---|---|
| `og_title` | Заголовок для соцсетей и мессенджеров |
| `og_description` | Описание ссылки |
| `og_image` | Картинка превью |
| `favicon` | Значок страницы |
| `page_bg` | Цвет фона страницы |
| `page_link_color` | Цвет ссылок |
| `custom_css` | Дополнительный CSS страницы, только суперадмин |
| `custom_js` | Дополнительный JS страницы, только суперадмин |
| `override_header`, `override_footer` | Включение локальных конфигураций |
| `header_config`, `footer_config` | Данные переопределённых зон |

Для `custom_css` и `custom_js` установлен лимит 20 000 символов. Это мощные настройки, поэтому сервер ограничивает их ролью суперадминистратора. Отдельные title, description и H1 управляются метаданными страницы.

### 13.3. Общая тема

Настройки темы позволяют централизованно управлять оформлением сайта и кириллическими шрифтами. Блоки могут наследовать базовые цвета и размеры, а локальная типографика и кнопочные стили переопределяют их точечно.

### 13.4. Header

Конфигурация верхней зоны поддерживает:

- логотип;
- меню до двух уровней;
- телефон и email;
- CTA-кнопку;
- социальные ссылки;
- sticky-режим;
- прозрачный вариант;
- высоту в допустимом диапазоне;
- использование глобальной конфигурации.

### 13.5. Footer

Нижняя зона поддерживает колонки ссылок, контакты, адрес, социальные сети, copyright, служебные badges и переключатель использования глобальных настроек. URL проходят валидацию, а текстовые поля ограничены по длине.

## 14. Роли, права и безопасность

### 14.1. Роли администраторов

| Роль | Основные доступы |
|---|---|
| `superadmin` | Все разделы, HTML-блок, custom CSS/JS страницы и блоков |
| `content` | Страницы, тема, меню, соцсети, SEO, сайт и резервные копии |
| `orders` | Дашборд, клиенты, чаты, интеграции и резервные копии |

Ограничения проверяются не только скрытием пунктов интерфейса, но и серверной логикой. Например, контент-администратор не может просто отправить HTML-блок через API в обход интерфейса.

### 14.2. Защитные механизмы

В проекте реализованы:

- CSRF-защита административных запросов;
- ограничение попыток входа и блокировка при подозрительной активности;
- проверка ролей;
- экранирование обычного текста;
- санитайзинг HTML;
- проверка ссылок и схем URL;
- белые списки шрифтов и иконок;
- проверка расширений, MIME и сигнатур загружаемых файлов;
- ограничения размеров и символов в CSS;
- аудит отдельных административных действий;
- защитные HTTP-заголовки и CSP в соответствующих сценариях.

Это не означает автоматическую production-готовность любого развёртывания. Нужно отдельно настроить секреты, пароли, HTTPS, резервное копирование, обновления зависимостей, права на файлы и мониторинг. Демонстрационные учётные данные из старого README нельзя использовать как безопасную конфигурацию.

## 15. Практические сценарии

### 15.1. Собрать обычный лендинг

1. Создать страницу по шаблону «Лендинг».
2. Проверить slug, title, description и H1.
3. Настроить обложку: `banner`, `text_image` или `zero`.
4. Добавить преимущества, галерею, отзывы и FAQ.
5. Добавить товары, если страница продаёт конкретную подборку.
6. Поставить форму или кнопку с нужным действием.
7. Настроить фон, отступы и типографику каждой секции.
8. Проверить Desktop, Tablet и Mobile; в Zero вручную поправить адаптивные координаты.
9. Заполнить OG-поля и проверить предпросмотр.
10. Сохранить именованную версию и опубликовать.

### 15.2. Собрать композицию в Zero-блоке

1. Добавить `zero` и задать высоту.
2. Сначала разместить крупные изображения и фигуры, затем текст и CTA.
3. Настроить слои и прозрачность, проверить читаемость.
4. Не увлекаться абсолютным позиционированием мелкого текста: при другом размере шрифта он может обрезаться.
5. Переключиться на Tablet, переместить и уменьшить нужные элементы.
6. Повторить для Mobile.
7. Проверить ссылки, контраст и отсутствие наложений на реальной ширине iframe.

### 15.3. Добавить товарную подборку

1. Убедиться, что товары уже импортированы и видимы в каталоге.
2. Добавить `products`.
3. Выбрать источник WB/Ozon, категорию или рекомендации.
4. Установить лимит.
5. Проверить цены, остатки и кнопки покупки на предпросмотре.
6. Опубликовать страницу.

Если каталог пуст, красивый блок не решит проблему: сначала нужно настроить данные и интеграции.

### 15.4. Повторно использовать фирменную секцию

Для разового повторения удобно сохранить блок в «Мои блоки». Для оригинальной сложной секции — вставить готовый `section` и править тексты внутри него. Для постоянно повторяющихся на всех страницах контактов и навигации правильнее использовать глобальные Header/Footer, а не десятки независимых копий.

## 16. Ограничения и особенности исследованной версии

Эти пункты важны для честной оценки: наличие поля в интерфейсе или JSON ещё не гарантирует полноценной функции.

1. **Инлайн-редактор обычных блоков сохраняет plain text.** Это защищает от случайной разметки, но не даёт постоянного Rich Text-форматирования выделенных слов. Секции перенесённого дизайна обрабатываются иначе и сохраняют HTML.
2. **Форма фиксирована.** Нельзя визуально добавлять произвольные поля, создавать условия, многошаговость, квиз или калькулятор.
3. **`recipient` — не почтовая маршрутизация.** Значение попадает в служебную заметку заявки.
4. **Ручные отзывы не связаны автоматически с модерируемой моделью `Review`.**
5. **Обычное видео поддерживает YouTube/Vimeo.** RuTube доступен в фоне и Zero, но не в самостоятельном блоке `video`.
6. **Настройки числа колонок требуют исправления.** В текущем commit `gallery.cols`, `features.cols` и рассчитанное число колонок `text_columns` не полностью подключены к итоговым CSS-классам серверного рендера.
7. **HTML сильно ограничен.** Даже суперадмин не получает произвольные script/style/iframe через HTML-блок. Это осознанная безопасность, но она снижает совместимость со сторонними виджетами.
8. **Zero-блок проще Tilda.** Нет групп элементов, Auto Layout, полноценного сложного позиционирования и богатой поэлементной анимации.
9. **Автосохранение не является совместным редактированием.** HTTP 409 защищает публикационный save, но не исключает перезапись черновика другим редактором.
10. **История ограничена 10 версиями.** Нет визуального diff и бессрочного журнала контента.
11. **README устарел.** В нём описана более ранняя версия с простым HTML-редактированием и заявлено, что ряд коммерческих функций не работает. Актуальный код содержит развитый блочный редактор, каталог, заказы, кабинет и другие модули; выводы нужно делать по коду и тестам, а не только по README.
12. **Git-архив не полностью самодостаточен для пресетов секций.** Каталог `data/` исключён через `.gitignore`; без локального `content.json` отсутствует и сгенерированный `section_presets.json`.

### 16.1. Проверка тестами

Был выполнен выборочный прогон тестов конструктора, блоков, действий кнопок, иконок, страниц и безопасности. Результат: **118 тестов пройдено, 2 не пройдено**.

Оба падения связаны с пресетами секций:

- в пустом наборе нет канонического пресета «Главный баннер»;
- отсутствует сгенерированный `data/section_presets.json`.

Это подтверждает проблему воспроизводимости данных Git-архива, но не доказывает отказ всего редактора. Для прогона также потребовалось создать отсутствующий каталог `data/image_cache`; исходный код проекта не изменялся.

## 20. Подробное сравнение по рабочим задачам

### 20.1. Архитектура и назначение

**Tilda** — универсальная SaaS-платформа: пользователь получает редактор, хостинг, публикацию, обновления и экосистему без необходимости сопровождать серверный код. Это удобно для быстрого запуска сайтов разных типов.

**Ekotoriya** — часть конкретного коммерческого приложения. Конструктор соседствует с товарами, остатками, заказами, клиентами, отзывами, чатами, рекомендациями и интеграциями WB/Ozon. Поэтому его главная ценность не в количестве универсальных дизайнов, а в возможности редактировать контент внутри собственного бизнес-процесса.

**Вывод:** для агентства и быстрого запуска множества независимых сайтов естественнее Tilda; для единого self-hosted магазина с особыми бизнес-правилами — Ekotoriya.

### 20.2. Добавление блоков и скорость старта

В обоих конструкторах страница собирается из секций, блоки можно переставлять, копировать и настраивать через панели. В Ekotoriya есть drag-and-drop из библиотеки и три стартовых шаблона, а структура помогает ориентироваться в длинной странице.

Tilda выигрывает по масштабу готовой библиотеки: сотни композиций позволяют выбрать уже решённый визуальный сценарий — обложку, тарифы, расписание, команду, портфолио, форму или карточки. В Ekotoriya одну и ту же визуальную задачу чаще придётся собирать из базового типа, настроек оформления или Zero.

**Вывод:** Ekotoriya имеет достаточный конструктивный минимум, но Tilda заметно сокращает путь от идеи до разнообразного готового дизайна.

### 20.3. Редактирование контента

Ekotoriya предлагает привычную схему: выбор на холсте, свойства справа, двойной клик для текста, undo/redo, горячие клавиши, масштаб и предпросмотр. Серверная модель JSON прозрачна и удобна для программной миграции.

Ограничение — plain text в обычном инлайн-режиме и фиксированный набор полей. В Tilda текстовые возможности и разнообразие контентных контролов богаче, а готовые блоки содержат больше специализированных настроек. При этом Ekotoriya проще расширить радикально: разработчик может добавить новое поле, тип блока и серверный рендер без ожидания функции платформы.

### 20.4. Zero-блок

Общая идея совпадает: элементы размещаются свободно, имеют размеры, слои и адаптивные состояния. В Ekotoriya уже реализованы не только базовые функции: поворот, resize с пропорциями, клавиатурная точность, z-index, скрытие и per-breakpoint-координаты.

Tilda Zero Block существенно глубже:

- больше типов элементов, включая форму, галерею, HTML, tooltip и vector;
- Grid/Window Container;
- группы, в том числе логические и объектные;
- Auto Layout;
- модульная сетка;
- больше стандартных и пользовательских диапазонов;
- покадровые и триггерные анимации.

У Ekotoriya процентные координаты просты и предсказуемы для разработчика, но требуют ручной адаптивной работы. Текст может обрезаться границами элемента, а кнопка Zero имеет меньше действий, чем самостоятельный блок кнопки.

**Вывод:** Zero Ekotoriya подходит для относительно простых авторских обложек и композиций. Для сложного editorial-дизайна и анимационных сцен Tilda сейчас сильнее.

### 20.5. Адаптивность

Same-origin iframe — сильная сторона Ekotoriya: редактор проверяет настоящий рендер страницы на заданной ширине. Общие CSS-правила и скрытие блоков покрывают базовые задачи, а Zero получает Tablet/Mobile overrides.

Tilda предоставляет более системную работу с диапазонами и свойствами. В Ekotoriya три кнопки устройства не эквивалентны пяти стандартным диапазонам Tilda: отсутствует произвольный пользовательский breakpoint, а у обычных блоков нет широкого набора независимых мобильных значений.

**Вывод:** базовый адаптивный сайт сделать можно, но сложные переходы между ширинами требуют CSS и проверки вне редактора.

### 20.6. Анимация и интерактивность

Ekotoriya анимирует появление целого блока одним из пяти эффектов, поддерживает задержку, длительность и sticky. Для обычного лендинга этого достаточно.

Tilda позволяет строить анимацию элементов по шагам и по триггерам, связывать её с прокруткой и действиями пользователя. Ekotoriya не имеет аналогичного визуального Timeline/Trigger-редактора. Дополнительную интерактивность придётся программировать.

### 20.7. Формы, заявки и попапы

Ekotoriya выигрывает в прямой связи с собственной админкой: форма создаёт заявку внутри того же приложения, где уже есть клиенты и заказы. Не требуется настраивать внешний приёмник для базового сценария.

Но как **конструктор форм** решение минимально: четыре фиксированных элемента и отсутствие визуального редактора схемы. Tilda сильнее по типам полей, компоновке, условиям, многошаговым сценариям, квизам и калькуляторам. Попапы Tilda также более универсальны как самостоятельные контентные блоки.

**Вывод:** для простой заявки Ekotoriya удобен; для маркетинговых форм и сложной лидогенерации нужна доработка или Tilda.

### 20.8. Магазин и интеграции

Здесь сравнение не сводится к «больше/меньше функций».

- **Tilda** даёт универсальные инструменты магазина и подключение типовых сервисов в облачной экосистеме.
- **Ekotoriya** хранит собственные товары и бизнес-состояние, работает с источниками WB/Ozon, ценами, остатками, избранным, покупкой, заказами и рекомендациями. Блок `products` напрямую использует эту модель.

Если бизнес-логика уже реализована в Ekotoriya, перенос её в универсальный конструктор может быть сложнее, чем развитие текущего редактора. Если нужен стандартный магазин без команды разработки, облачная платформа обычно практичнее.

### 20.9. CMS и повторяющийся контент

В Ekotoriya есть много специализированных моделей, но нет универсального визуального механизма коллекций уровня Tilda Потоков. Нельзя просто создать произвольную сущность «Кейсы» с набором полей и автоматически генерировать страницы через админку конструктора.

Для товаров, отзывов, чатов и заказов специализированные модели хороши. Для статей, кейсов, команд, объектов и других произвольных коллекций потребуется проектировать новые модели и интерфейсы. Tilda в этом сценарии более универсальна.

### 20.10. Медиатека и дизайн-система

Ekotoriya предоставляет повторный выбор файлов, безопасную загрузку, типографику, кнопочные стили, общую тему и глобальные зоны. Этого достаточно для поддержания единого небольшого сайта.

Tilda имеет более зрелую экосистему готового дизайна и настроек. Однако Ekotoriya даёт возможность жёстко контролировать дизайн-систему в коде: белые списки шрифтов, иконок и ограничения значений уменьшают риск визуального хаоса.

### 20.11. SEO и публикация

Ekotoriya покрывает базовые потребности: title, H1, meta, OG, favicon, slug, фон и ссылки страницы. Публикация отделена от черновика, а восстановление версии происходит безопасно через draft.

Tilda предлагает более широкий набор встроенных SEO- и публикационных инструментов, удобных нетехническому специалисту. В Ekotoriya часть задач — sitemap, robots, редиректы, серверные заголовки, аналитика и производительность — нужно оценивать и настраивать на уровне всего приложения и инфраструктуры, а не только страницы.

### 20.12. Совместная работа и история

В Ekotoriya есть 50 шагов undo/redo внутри редактора, автосохранение, до 10 версий и 409 при устаревшем save. Это хорошая защита одиночного редактора и простой последовательной работы команды.

Но real-time co-editing отсутствует, а конфликт черновиков возможен. Для команды нужен регламент: один основной редактор страницы в момент времени, именованные версии перед большими изменениями и публикация после проверки. Tilda как облачный сервис удобнее для типовой командной эксплуатации, хотя конкретные права и история зависят от аккаунта.

### 20.13. Код, роли и безопасность

Ekotoriya даёт три роли и серверные ограничения опасных функций. Санитайзер HTML и запреты CSS снижают риск инъекций, но ограничивают вставку внешних виджетов. Открытый код позволяет провести аудит и исправить проблему самостоятельно.

Одновременно self-hosted означает полную ответственность команды: уязвимость зависимости, слабый пароль, неправильная CSP или отсутствие резервной копии становятся проблемой владельца. В Tilda большая часть платформенной безопасности централизована, но пользователь ограничен её моделью разрешений и настройками.

### 20.14. AI и скорость производства

В исследованном Ekotoriya нет встроенного AI-генератора блоков или контента. Tilda имеет AI-функции и Vibe Block, способные ускорить создание новой композиции. Для Ekotoriya аналогичный сценарий потребует отдельной интеграции и контроля генерируемого JSON/HTML.

### 20.15. Стоимость владения

Нельзя корректно сравнить только подписку Tilda и «бесплатный» хостинг Ekotoriya.

Для Ekotoriya в стоимость входят:

- сервер и база данных;
- домен, HTTPS и мониторинг;
- резервные копии;
- время разработчика;
- исправление ошибок и обновление зависимостей;
- сопровождение WB/Ozon и других интеграций;
- развитие самого редактора.

Для Tilda — подписка, ограничения тарифа и возможные сторонние сервисы, но меньше эксплуатационной работы. Экономический выбор зависит от того, нужна ли уникальная серверная логика.

## 21. Что выбрать

### 21.1. Tilda подходит лучше, если

- нужно быстро запустить лендинг, портфолио, сайт события или типовой магазин;
- важна большая библиотека готового дизайна;
- сложную страницу планируется собирать в Zero Block с анимацией;
- нужны гибкие формы, квизы, калькулятор или универсальные коллекции;
- нет постоянной команды backend/DevOps;
- приемлема работа в рамках облачной платформы и её тарифов.

### 21.2. Ekotoriya подходит лучше, если

- проект уже является этим магазином и использует его заказы, товары и интеграции;
- требуется полный контроль над исходным кодом, БД и файлами;
- нужны особые бизнес-правила, которые проще реализовать в Python;
- команда готова сопровождать сервер, безопасность и резервные копии;
- достаточно 23 базовых типов и несложного Zero;
- редактор нужен в первую очередь контент-менеджеру, а не дизайнеру сложных интерактивных сцен.

### 21.3. Прагматичный итог

**Tilda сейчас сильнее как универсальный визуальный конструктор.** Она выигрывает по библиотеке, Zero Block, адаптивным диапазонам, анимации, формам, CMS и AI.

**Ekotoriya сильнее как настраиваемая часть собственного коммерческого продукта.** Его преимущество — открытая архитектура и непосредственная связь контента с реальными товарами и бизнес-данными.

Поэтому заменять Tilda на Ekotoriya только ради конструктора нерационально. Развивать встроенный редактор Ekotoriya рационально, если он решает задачи существующего магазина и уменьшает зависимость контент-менеджеров от разработчиков.

## 22. Приоритеты развития Ekotoriya

Если цель — приблизить редактор к зрелому конструктору, разумный порядок работ такой:

1. **Исправить расхождения UI и рендера:** колонки галереи, преимуществ и текстовых колонок; добавить регрессионные тесты, проверяющие итоговые классы.
2. **Сделать данные воспроизводимыми:** поставлять безопасный минимальный `content.json`/fixture или генерировать пресеты при установке; автоматически создавать `image_cache`.
3. **Обновить README:** описать актуальный редактор, запуск, роли, данные, публикацию и ограничения.
4. **Улучшить обычный текст:** безопасный Rich Text с белым списком форматирования, ссылками и списками вместо потери инлайн-разметки.
5. **Расширить формы:** схема полей, обязательность, типы, сообщения, отдельные приёмники и тесты заявок.
6. **Углубить адаптивность:** произвольные ширины предпросмотра и per-breakpoint-настройки важных свойств обычных блоков.
7. **Развивать Zero:** группы, выравнивание/распределение, направляющие, копирование элементов, независимые мобильные стили и предупреждение о переполнении текста.
8. **Добавить универсальные коллекции:** только если проекту действительно нужны статьи, кейсы и другие повторяющиеся сущности.
9. **Усилить совместную работу:** optimistic locking для черновика, историю автора изменений и более длинный архив версий.
10. **Не ослаблять безопасность ради HTML-совместимости:** сторонние виджеты лучше подключать через отдельные проверенные типы интеграций, а не через неограниченный script для всех редакторов.

Основной источник: репозиторий [Un1v4rse/ekotoriya](https://github.com/Un1v4rse/ekotoriya), commit [`474d39fd253b4a4dc8591da766129ec9c40c0cbe`](https://github.com/Un1v4rse/ekotoriya/tree/474d39fd253b4a4dc8591da766129ec9c40c0cbe) от 28 октября 2026 года.

## Приложение В. Границы исследования

- Анализ Ekotoriya основан прежде всего на исходном коде и тестах зафиксированного commit, а не на предположениях по скриншотам.
- Полный production-аудит производительности, уязвимостей, всех интеграций и качества вёрстки на реальных устройствах не проводился.
- Выборочный тестовый прогон не эквивалентен полному приёмочному тестированию магазина.
- Число блоков Tilda и её функции описаны по официальной документации; сравнение не утверждает, что каждая функция доступна на каждом тарифе.
- Выводы о нереализованных возможностях Ekotoriya относятся к исследованному commit и могут измениться в следующих версиях.
